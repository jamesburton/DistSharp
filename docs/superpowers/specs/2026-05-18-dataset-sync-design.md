# DistSharp — Dataset Sync (HF + Git) Design

**Date:** 2026-05-18
**Status:** Design / planning. Not yet implemented.
**Scope:** New `dataset` command group on the CLI — `pull`, `push`, `merge`, `sync` — covering Hugging Face Hub dataset repos and any git-based dataset repository.

---

## 1. Goals

A generated dataset is not a snapshot — the codebase it was generated from keeps changing. Today, `distsharp generate` regenerates everything from scratch on every run, and `distsharp export --hf-repo` is a write-only push. The result: re-running against a slightly-changed solution burns tokens for thousands of rows whose source symbols haven't moved.

This design adds four operations so a generated dataset can be treated like a living, versioned artifact:

| Operation | Direction | Purpose |
|---|---|---|
| `dataset pull` | remote → local | Fetch the current state of a dataset repo into a local directory. |
| `dataset push` | local → remote | Send the local directory back to the dataset repo. |
| `dataset merge` | local + local → local | Combine two local snapshots with a conflict policy. |
| `dataset sync` | local + solution → local + remote | "Make the dataset reflect the current state of the solution, regenerating only what changed, then push." |

Two transport backends are supported on day one: **Hugging Face Hub** (datasets, currently the only remote DistSharp pushes to) and **plain git** (any repo accessible by a `git` URL, including Azure DevOps, GitHub, GitLab, self-hosted).

---

## 2. Why this is hard (and what makes it tractable)

Two facts about DistSharp datasets make sync feasible:

1. **Every row has a stable upstream identity.** Each row was generated from a Roslyn `ExtractedSymbol`, which has a fully-qualified name. The pair `(symbol_fqn, dataset_type)` is a natural, stable primary key. Re-running the pipeline always yields the *same key* for the same symbol — only the row contents differ.
2. **Symbol bodies are content-addressable.** Hash the symbol's normalised source body and you get a deterministic content marker. A row is "still fresh" iff its stored body-hash matches the current solution's body-hash for that symbol.

Together, those two facts turn sync from "diff two arbitrary JSONL files" (intractable) into "diff two sets of `(key, body_hash)` pairs" (a 20-line algorithm). The hard problem is plumbing — getting bytes in and out of HF / git cleanly — not the diff itself.

## 3. Dataset on-disk layout

A DistSharp dataset directory has, in addition to the existing data files, a manifest:

```
my-dataset/
  _distsharp/
    manifest.json              # source-of-truth row index
    pipeline.snapshot.yaml     # frozen copy of the pipeline config that produced this state
    schema.json                # row schema for the dataset_type(s) present
  data/
    train.jsonl                # or .parquet — existing writers, unchanged format
    validation.jsonl           # optional split
  README.md                    # HF dataset card (autogenerated, user-editable)
  .gitattributes               # `*.parquet filter=lfs diff=lfs merge=lfs -text` for git LFS
```

The pre-existing JSONL/Parquet writer output is unchanged — sync wraps around them, it does not rewrite them.

### `_distsharp/manifest.json`

```jsonc
{
  "format_version": 1,
  "generated_at": "2026-05-18T12:34:56Z",
  "source": {
    "solution_path": "MyApp.sln",
    "solution_sha": "git-sha-of-the-solution-at-generation-time",
    "commit": "feature/9933-config-driven-temp-file-service@a1b2c3d"
  },
  "rows": [
    {
      "id": "abc123…",                                // stable row id (see §4)
      "symbol_fqn": "MyApp.Services.OrderService.PlaceOrderAsync",
      "symbol_kind": "method",
      "dataset_type": "explanation",
      "body_sha": "sha256 of normalised body",
      "prompt_version": "explanation@2",
      "row_offset": 142                                // line index into data/train.jsonl
    },
    …
  ]
}
```

The manifest is the only file `dataset merge` / `sync` need to read fully. The JSONL itself is touched only when rows actually change.

## 4. Row identity

```
row_id = sha256(
    symbol_fqn || "\n" ||
    dataset_type || "\n" ||
    prompt_version
)[:16]
```

- Stable across runs.
- Independent of body — so when the body changes, the row id stays the same and the row is rewritten in place.
- 16-hex prefix is short enough to be human-eyeballable and collision-free for the dataset sizes DistSharp targets (≤ ~1 M rows).

`body_sha` is a *separate* field. The pair `(row_id, body_sha)` tells you everything:

| Old `row_id` exists in remote? | `body_sha` matches local? | Action on `sync` |
|---|---|---|
| no | n/a | new row — generate and add |
| yes | yes | unchanged — skip |
| yes | no | stale — regenerate, replace in place |
| local has no symbol for it | n/a | orphan (symbol deleted) — see §6 for policy |

## 5. Transport backends

### Hugging Face Hub

Builds on the existing `HuggingFaceClient` (currently push-only via `export --hf-repo`). Three additional capabilities needed:

| Method | HTTP call | Purpose |
|---|---|---|
| `ListFilesAsync(repo, branch)` | `GET /api/datasets/{repo}/tree/{branch}` | Enumerate files for pull. |
| `DownloadFileAsync(repo, branch, path)` | `GET /datasets/{repo}/resolve/{branch}/{path}` | Stream one file. |
| `DeleteFileAsync(repo, branch, path)` | `DELETE /api/datasets/{repo}/{path}` (uses commit endpoint) | Remove orphaned files. |

HF datasets are git-LFS-backed for files > 10 MB. The existing upload path already uses the `upload-file` LFS endpoint; the download path needs the LFS-aware resolve URL (HF rewrites `resolve/` URLs to LFS pointers automatically — handled server-side).

Auth: existing `HF_TOKEN` env var.

### Git

Shell out to `git` (already on PATH for any developer who installed DistSharp via `dnx`). Operations are just:

- `pull`  → `git clone --depth 1 <url> <dir>` (or `git fetch && git reset --hard origin/<branch>` for an existing local clone)
- `push`  → `git add -A && git commit -m "<msg>" && git push origin <branch>`
- `merge` → done locally (DistSharp's merge operates on manifest+files), then a single commit

The git-as-transport implementation lives in `DistSharp.Core/Sync/GitTransport.cs` and is intentionally minimal — it does **not** wrap full git semantics, it wraps "fetch this snapshot" / "push that snapshot". When the user has 3-way merge needs that git itself solves better (`git rerere`, custom merge drivers), they should run plain git in the directory.

### Backend selection

```bash
# HF (default if URL host is huggingface.co)
distsharp dataset pull my-org/my-dataset --into ./datasets/my-dataset

# Git (explicit)
distsharp dataset pull --git-remote https://github.com/me/my-dataset.git --into ./datasets/my-dataset

# Mixed: pull from HF, push to git mirror
distsharp dataset push ./datasets/my-dataset --git-remote https://github.com/me/my-dataset-mirror.git
```

A dataset directory remembers its remote in `_distsharp/manifest.json` under a `remotes: { hf: …, git: … }` map, so the second push (and subsequent syncs) doesn't need the URL again.

## 6. Merge & conflict resolution

Two snapshots A and B are merged by walking the union of `row_id`s in their manifests:

| Row in A? | Row in B? | `body_sha` match? | Default action |
|---|---|---|---|
| ✅ | ❌ | n/a | take A |
| ❌ | ✅ | n/a | take B |
| ✅ | ✅ | yes | keep (identical) |
| ✅ | ✅ | no | **conflict** |

Conflict policies (`--strategy`):

- `ours` — keep A (the one named first on the command line).
- `theirs` — keep B.
- `newer` — keep whichever has the later `generated_at` in its manifest.
- `regenerate` — drop both, mark for regeneration on the next `sync`.
- `prompt` — write both into `_distsharp/conflicts/<row_id>.json` and require the user to resolve.

Default: `newer` — matches the "datasets evolve as code evolves" framing and avoids surprising data loss.

### Orphans

A row whose `symbol_fqn` no longer exists in the current solution is an orphan. Policies:

- `keep` — leave it (good if the dataset is shipped publicly and historical examples matter)
- `drop` — remove (default for `sync`, since the goal is "reflect current state")
- `archive` — move into `_distsharp/archive/<date>.jsonl` (good when the symbol was renamed and you may want to hand-restore)

## 7. CLI surface

```bash
# Plain fetch — no regeneration
distsharp dataset pull <repo-or-url> [--branch main] [--into <dir>]

# Plain push — fails if remote has diverged unless --force
distsharp dataset push <dir> [--hf-repo <repo> | --git-remote <url>] [--branch main] [--message "<commit msg>"] [--force]

# Combine two local snapshots
distsharp dataset merge <dir-a> <dir-b> --out <dir-c> [--strategy newer|ours|theirs|regenerate|prompt]

# The big one — make the dataset match the solution, regenerate stale rows, push
distsharp dataset sync <dir> \
  --solution <sln> \
  [--remote auto|hf|git]            # default: whichever is recorded in manifest
  [--orphan-policy drop|keep|archive] \
  [--push]                           # default: no push, just report+regenerate locally
  [--dry-run]                        # show plan without doing it
```

`sync` is the headline command. Its execution plan, given an existing dataset dir and a solution:

```
1. dataset pull  (refresh local from remote)              [skipped if --remote none]
2. Run RoslynSymbolExtractor against the solution.
3. Compute current set of (symbol_fqn, body_sha).
4. Diff against manifest.json:
     - new symbols       → run LlmStep for them only
     - stale rows        → run LlmStep for them only
     - unchanged rows    → no LLM call
     - orphans           → apply orphan-policy
5. Rewrite manifest + affected data files.
6. dataset push  (write changes back)                     [if --push]
```

Cost model: re-running on a hot codebase touches O(changed-symbols) tokens, not O(all-symbols). For most working days that means a sync is ~100× cheaper than a full regenerate.

## 8. Components & file layout

```
src/DistSharp.Core/
  Sync/
    DatasetManifest.cs                # the model from §3
    RowIdentity.cs                    # the hashing rules from §4
    DatasetDiff.cs                    # pure-function diff over two manifests
    MergeStrategies.cs                # the policies from §6
    IDatasetTransport.cs              # pull/push/list/delete contract
    HuggingFaceDatasetTransport.cs    # HF-specific implementation
    GitDatasetTransport.cs            # git-specific implementation
    DatasetSyncOrchestrator.cs        # the §7 sync plan

src/DistSharp.Cli/
  Commands/
    DatasetPullCommandHandler.cs
    DatasetPushCommandHandler.cs
    DatasetMergeCommandHandler.cs
    DatasetSyncCommandHandler.cs
```

`DistSharp.Core.Sync` is in `Core` (not the CLI) because the orchestrator needs `RoslynSymbolExtractor`, `LlmStep`, and `IDatasetWriter` — all `Core` types. The CLI handlers are thin wrappers that bind flags to orchestrator calls.

## 9. Compatibility with existing `export`

The current `distsharp export --hf-repo <repo>` is preserved unchanged. It becomes effectively a special case of `dataset push`:

| Old | New equivalent |
|---|---|
| `distsharp export ./out --hf-repo me/data` | `distsharp dataset push ./out --hf-repo me/data` |
| `distsharp export ./out --format alpaca --out-dir ./alpaca` | unchanged — `export` keeps the format-conversion role |

`export`'s format-conversion responsibility (jsonl → alpaca → sharegpt) is distinct from sync's transport role and stays in `export`.

The first time `dataset sync` writes to a directory, it injects the `_distsharp/manifest.json`. Existing datasets generated before sync was added get a one-time `dataset migrate <dir> --solution <sln>` to compute and seed the manifest from current data; after that, sync works normally.

## 10. Effort

| Phase | Scope | Estimate | Dependencies |
|---|---|---|---|
| **1: Manifest + identity** | `DatasetManifest`, `RowIdentity`, `DatasetDiff`, write manifest on every existing run | 2 days | none |
| **2: pull + push** | Both transports, `dataset pull` / `dataset push` commands | 3 days | Phase 1 |
| **3: merge** | `dataset merge` with all strategies | 2 days | Phase 1 |
| **4: sync** | `DatasetSyncOrchestrator` + `dataset sync` command | 3 days | Phases 1 + 2 |
| **5: migrate** | One-shot manifest seeding for legacy directories | 1 day | Phase 1 |

**Total: ~11 working days for full sync.** Each phase is independently shippable.

The fastest *useful* slice is Phase 1 + Phase 4 with sync running locally only (no `--push`), which gives the headline "regenerate just what changed" workflow in ~5 days without any transport work — meaningful even before `pull` / `push` land.

## 11. Risks & open questions

1. **JSONL line edits.** Rewriting one row in a 50k-row JSONL means rewriting the whole file. Acceptable for now (writes are still cheap; pulls already re-fetch the whole file). If it becomes a bottleneck, partition the dataset into multiple JSONL files keyed by `row_id` prefix.
2. **LFS round-trips on HF.** Parquet output for large datasets goes via git-LFS on HF. Pull bandwidth is fine; push needs the existing LFS upload path. Already implemented for `export`.
3. **Git history bloat.** Committing a regenerated 50k-row JSONL every day will balloon git history. For git remotes, recommend `git checkout --orphan` periodically or just use HF (which is content-addressable LFS — no history bloat).
4. **Concurrent sync from two machines.** Last-writer-wins on the remote, plus a conflict on the next pull. The conflict policies in §6 handle this; the manifest's `generated_at` lets `newer` strategy resolve sensibly.
5. **Prompt-version drift.** If `prompt_version` changes (e.g. you edit the explanation prompt), *every* row becomes stale by §4's rules. That's correct — the dataset has different semantic content — but expensive. Add a `--prompt-version-override <version>` escape hatch to claim "this prompt change is non-substantive, treat rows as still fresh."
6. **Solution renames / refactors.** When a class moves namespace, every `symbol_fqn` under it changes and every row becomes orphan + new. Mitigation: an optional `--rename-map old=new,old=new` flag, or a heuristic that pairs orphan-of-the-same-body-sha with new-of-the-same-body-sha and treats them as renames. Heuristic is post-v1.

---

## 12. Out of scope

- **Argilla / Label Studio integration** (curation UI). Sync is a programmable substrate; curation is a separate workflow.
- **Federated sync across many HF repos** ("pull from these 5 repos and merge"). Build by composing `pull` + `merge`; no new primitive needed.
- **Pull-request-style review on HF.** HF supports community discussions on dataset repos; we surface URLs in `dataset push` output but don't try to open PRs programmatically.
- **Streaming row-level updates** (push one row at a time). The unit of operation is "a manifest snapshot," not "a row."
